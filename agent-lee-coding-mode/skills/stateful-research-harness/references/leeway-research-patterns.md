# Leeway Research Patterns

## Pattern: internal source-of-truth discovery

Use for questions about Leeway/Beast-AI projects, processes, customers, roadmap, partnerships, product details, or internal decisions.

Procedure:
1. Identify likely systems of record: current conversation files, GitHub repos, docs, email, calendar, contacts, tickets, or other available connectors.
2. Search exact terms and likely aliases.
3. Prefer maintained docs and committed code over chat fragments.
4. Identify owner, date, repo/path, and whether the artifact looks official.
5. Summarize gaps if the connector or expected source is unavailable.

Output emphasis:
- What is confirmed.
- What is inferred.
- What is missing.
- Who or what source should be checked next.

## Pattern: product and architecture assessment

Use for APIs, repos, models, integrations, infrastructure, benchmarks, or implementation feasibility.

Procedure:
1. Capture exact version, repo, branch, model, API, or environment assumptions.
2. Read canonical docs and source code before tutorials or commentary.
3. Identify external dependencies, credentials, runtime requirements, and operational constraints.
4. Separate prototype feasibility from production readiness.
5. Produce test plan and rollout path.

Output emphasis:
- Proposed design.
- Dependencies.
- Failure modes.
- Validation plan.
- Production-readiness gaps.

## Pattern: competitive or market scan

Use for competitors, customer segments, partner research, pricing, positioning, and GTM analysis.

Procedure:
1. Start with company-owned/public primary sources.
2. Add reputable secondary sources for market interpretation.
3. Record dates and likely bias.
4. Convert facts into implications for Leeway.
5. Avoid pretending uncertain market claims are hard facts.

Output emphasis:
- Decision relevance.
- Differentiation.
- Risks.
- Evidence-backed recommendations.

## Pattern: claim audit

Use when reviewing a memo, pitch, answer, PRD, research note, or strategy doc.

Procedure:
1. Extract atomic claims.
2. Classify each claim by type and risk.
3. Verify high-risk and load-bearing claims first.
4. Mark claims supported, unsupported, contradicted, ambiguous, or not checked.
5. Suggest safer wording for weak claims.

Output emphasis:
- Keep/modify/remove recommendations.
- Replacement language.
- Evidence gaps.
